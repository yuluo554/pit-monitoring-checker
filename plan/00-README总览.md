# pit-monitoring-checker · 总览

建筑基坑工程监测数据判读与预警工具（离线桌面 exe，规则优先，零 LLM、零网络，判定挂条款号）。

**它管的是一座基坑从开挖到封底的全部量测读数**：台账持久、阈值来源可溯、"报警未处置"能一路跟着下一个轮次。
大模型聊天框没有你的上一轮数据，也不会替你守住"超标未闭环不得进入下一工况"这条纪律。

## 当前状态：M5 交付形态完成 ✅（2026-10-07）—— 功能面五模块全通，只剩发布

```bash
python -X utf8 -m pmc selfcheck     # 契约自检：依据登记 5 条 / 字典 14 项 / 规则 17 条 → SELF_CHECK_OK
python -X utf8 -m pmc init --db ledger.sqlite   # 建 11 张表的空台账
python -X utf8 -m pmc rulesets      # 可参与判定的规则 0 条（全部待原文核对，按纪律输出待定值）
python -X utf8 -m pmc synth --check            # 与仓内 62 个合成产物逐字节对账
python -X utf8 -m pmc bench                    # 内置基准：逐起 11 起对账 + 四态指标 + golden 位级对账
python -X utf8 -m pmc report --kind daily --db ledger.sqlite --project SYN-ZHDQ --round 9   # xlsx 报告
python -X utf8 -m pytest -rs        # 440 项守门测试，py3.8 与 py3.12 全绿 0 跳过
```

M0 契约级骨架 → M1 数据面 → M2 判定内核与 XLSX 输入 → M3 条款核对与合规检核 → M4 基准评测 → M5 交付形态：
三座虚拟基坑（8/20/30 轮 × 每轮 196 行测点，共 11369 行观测、11 起事件真值）、CSV/XLSX 导入器与导入回执、
观测修订链、双控判定与未闭环延续、四类时序合规检核、内置基准评测，
以及 `pmc selfcheck / init / dict / rulesets / synth / import / ledger / check / audit / bench / report / gui` 十二条命令全部落地（无占位命令）。

M5 交付三件：
① `pmc report --kind daily|weekly|stage` —— 标准库 `zipfile` 直写 OOXML（零第三方依赖，`06 D03`/`D34`），
九张工作表含**原生过程线图**（`xl/charts`，不是贴图）与**追溯清单**（每个含数字的单元格挂 `(表, 行号, 列)`），
两次导出逐字节一致，签字栏空白即未审核，每份报告带"不判基坑是否安全"边界句（`plan/11`）；
② PySide6 五页签界面（台账 / 导入 / 判定 / 检核 / 报告）—— **只消费同一条 CLI 命令链**，
参数面是 CLI 的子集（测试逐个校验旗标），反馈走 notify 通道不用模态框，offscreen 冒烟常驻；
③ PyInstaller onedir 双 exe（`pmc.exe` 控制台 + `pmc-gui.exe` 界面）+ `scripts/dist_audit.py` 构建红线审计
（内嵌数据整目录逐份 sha256 对账、禁区成分、个人标记诱饵、报告 0 外链，9 项伪造产物反证常驻测试）。

**M5 的既成事实（不是缺陷）**：exe 现场演示链跑通「导入一轮 → 判定 → 导出日报」，
但判定出的是 196 行**待定值**、报告阈值列全空并带原因码 —— 因为数据面仍一条阈值都没核对
（`data/rulesets` 全 pending、测点档案无控制值）。数值通路仍只有两条合法入口：
① 用户在测点档案录入设计报警值；② 材料到位后按 `08 §三` 的分档结构填。
本轮**没有**为了让报告里出现数字而把夹具档位或合成档位搬进 `data/`（禁项一）。
