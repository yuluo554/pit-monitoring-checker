# pit-monitoring-checker · 总览

建筑基坑工程监测数据判读与预警工具（离线桌面 exe，规则优先，零 LLM、零网络，判定挂条款号）。

**它管的是一座基坑从开挖到封底的全部量测读数**：台账持久、阈值来源可溯、"报警未处置"能一路跟着下一个轮次。
大模型聊天框没有你的上一轮数据，也不会替你守住"超标未闭环不得进入下一工况"这条纪律。

## 当前状态：M3 条款核对 + 频率时效检核 ✅（2026-10-07）

```bash
python -X utf8 -m pmc selfcheck     # 契约自检：依据登记 5 条 / 字典 14 项 / 规则 17 条 → SELF_CHECK_OK
python -X utf8 -m pmc init --db ledger.sqlite   # 建 11 张表的空台账
python -X utf8 -m pmc rulesets      # 可参与判定的规则 0 条（全部待原文核对，按纪律输出待定值）
python -X utf8 -m pmc synth --check            # 与仓内 62 个合成产物逐字节对账
python -X utf8 -m pytest -rs        # 331 项守门测试，py3.8 与 py3.12 全绿 0 跳过
```

M0 契约级骨架 → M1 数据面 → M2 判定内核与 XLSX 输入 → M3 条款核对与合规检核：三座虚拟基坑（8/20/30 轮 × 每轮 196 行测点，共 11369 行观测、11 起事件真值）、
CSV/XLSX 导入器与导入回执、观测修订链、双控判定与未闭环延续，以及 `pmc synth / import / ledger / check / audit` 五条命令。

基准评测（M4）、报告与界面（M5）**尚未开工**。未开工命令返回退出码 3 并指回里程碑号。
M2 同时交付了 P07 拍板的 XLSX 输入通路：`pmc import` 认 `.xlsx`，行级校验与 11 个原因码与 CSV 完全共用一套。
M3 交付 `pmc audit` 四类时序检核（漏测 / 超间隔 / 工况变更后仍按旧频率 / 报警后未加密观测），逐条挂 `rule_id` + 条款号 + 可复算证据，只报「应核实」。

**M3 的核对结论本身就是一条交付物**：GB 50497-2019 的条文原文**没有官方可直连页面**（国家标准馆条目只提供到馆阅读/购买；
国家标准全文公开系统明示工程建设类国标未纳入收录；建标库渠道 TLS 证书主机名不符），37 号令正文在 gov.cn 域内检索零命中，
所以登记表里条文级条目全部保持 `pending`、一条数值都不供货（`plan/08 §二`）。
数据面上仍一条阈值都没有（`data/rulesets` 全 pending、测点档案无控制值），所以不带夹具档位时 `pmc check` 出 1568 行待定值、
`pmc audit` 出零违规 + 6 条不生效规则，两者退出码都是 1 —— 这是纪律在生效，不是缺陷。
