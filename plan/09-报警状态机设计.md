# 09 · 报警状态机与有效阈值选取（M2 定稿）

> 本文件是 `03 §1` 契约与 `03 §4` 判定接口的**落地细则**：引擎只按这里的次序与定义出结论。
> 改本文件的选取次序、未闭环定义、退出码触发集合 = 口径变更，须在 `06` 记一行并重跑 M2 回归。
> 术语：`判据（basis）`= 累计量 / 速率 / 预警比例；`测点档案` = `point` 表；`夹具` = `tests/fixtures/`。

## 一、判据适用范围：由字典决定，不由规则集决定

一条 (测点 × 轮次 × 监测项目) 要判哪些判据，取自 `data/dict/monitoring_items.json` 的 `control_kind`：

| `control_kind` | 适用判据 | 本项目里有谁 |
|---|---|---|
| `dual` | 累计量 + 速率 | 12 项（顶部水平/竖向位移、深层水平位移、立柱竖向、坑底隆起、支撑轴力、锚索轴力、水位、地面/建筑竖向、管线竖向、土体水平） |
| `cumulative` | 仅累计量 | `building_tilt`、`crack_width`（规范只给累计控制值，没有速率档） |
| `rate` | 仅速率 | 本项目字典里暂无 |
| `none` | 都不判 | 暂无 |

规则集的作用是**两件**：① 提供标准条文回退档的数值与条款号；② 提供速率窗口长度（`window_days` + `window_source`）。
所以"某项没有规则"不等于"不判它"——累计判据仍可由测点档案供货；但"速率判据没有窗口"就是无法计算（见 §三）。

## 二、有效阈值选取次序（每个判据独立走一遍）

```
1  测点档案 design_value/user_input 档   ← 首选（现场录入的真实控制值）
2  规则集 standard_value 回退档           ← 档案没有时用，必须带已核对的条款号
3  两者皆缺                               → 该判据 undetermined，并登记不启用原因码
```

### 2.1 第一档：测点档案

从 `point` 取 `design_cum_value`/`design_cum_unit` 与 `design_rate_value`/`design_rate_unit`，
连同 `threshold_source_kind`/`threshold_status`/`threshold_evidence`/`clause_ids` 组装成 `Threshold`，
再交给 `Threshold.disabled_reason()` 单点裁决（引擎不复述它的判据）。三条本层附加纪律：

| 纪律 | 原因码 | 说明 |
|---|---|---|
| 数值与单位必须同生同灭 | `value_missing` / `unit_missing` | 由 `disabled_reason()` 已有语义覆盖 |
| 档案单位必须等于字典单位（速率档为 `<字典单位>/d`） | `unit_inconsistent`（引擎级，见 §2.4） | 有人把 25 mm 的控制值填成 `cm`，供货就是错的，宁可待定 |
| 档案登记为 `standard_value` 时不得供货 | `evidence_missing` | `point` 表没有 `channel/url/verified_on` 三列，标准条文必须走第二档在规则集里登记全四件套 |

第三行不需要新代码：`Threshold.disabled_reason()` 对 `standard_value` 检查四件套，缺了自然不供货。

### 2.2 第二档：规则集标准回退

取该监测项目、同判据、`judgement=alarm` 的规则（同判据多条规则时取 `id` 字典序第一条，并在结论里登记该 `rule_id`）。
生效条件 = `rules/gate.threshold_block_reason()` 返回可用，即数值四件套齐备 **且** 其 `clause_id` 在依据登记表里 `verified`。

**条款号强制**：走第二档供货的判据，落库行的 `clause_ids` 必须含该条款登记键（`AlarmRecord.validate()` + DDL CHECK 双重把守）。

### 2.3 双控合成（`03 §4` 的细则）

| 情形 | 状态 | `trigger_basis` | 落库阈值列 | 备注 |
|---|---|---|---|---|
| 两判据都可判，至少一个越线 | `alarm` | 两个都越线 = `both`；否则单个判据名 | 两列都写实数 | 同轮多判据取重，不重复出两行 |
| 两判据都可判，都没越线 | `normal`（或达预警比例时 `prewarning`） | `none` | 两列都写实数 | |
| 一个可判、一个待定 | 按可判的那个出结论 | 可判侧的结果 | 可判侧写实数，待定侧**阈值为空 + 原因码** | 降级退出码 1；这就是"部分供货"必须显性化的落点 |
| 两判据都待定 | `undetermined` | `none` | 两列都空 | 不得渲染成"正常" |
| 本轮无有效读数（缺测/被拒收） | **不出行** | — | — | 状态机跳过该轮，`prev_state` 取上一个有读数的轮次；漏测本身是模块 3 的 `missed` 违规 |

`undetermined` 行的阈值列同时受 DTO（`AlarmRecord.validate()`）与存储层（`alarm_state` 的 CHECK）把守，
两处都要红才算这条纪律落地（`tests/test_alarm_engine.py` 与 `tests/test_db_schema.py` 各证一面）。

### 2.4 原因码集合：阈值轴 + 引擎轴分开

**阈值轴**（`contract/thresholds.py` 的 9 个码，口径 C2 不变）：`no_source`、`source_not_confirmed`、
`located_value_missing`、`value_missing`、`unit_missing`、`evidence_missing`、`clause_id_missing`、
`window_unconfigured`、`clause_not_verified`。

**引擎轴**（M2 新增，只在 `alarm_state.disabled_reasons` 出现，不进核对队列的阈值统计）：

| 码 | 含义 | 为什么不能塞进阈值轴 |
|---|---|---|
| `no_applicable_rule` | 该判据既无档案值也无规则（连回退档登记在哪都不知道） | 阈值轴的 `no_source` 说的是"这条阈值没挂来源"，此处是"根本没有这条判据的登记载体"，处置动作是补规则集而不是核对数值 |
| `unit_inconsistent` | 档案登记的单位与字典单位不符 | 阈值轴的 `unit_missing` 说的是"没写单位"，此处是"写了且写错了"，处置动作是改档案 |

落库文本 = 两轴原因码合并后按字典序 `;` 连接（同一行内去重），所以 `alarm_state.disabled_reasons` 可直接对账。

## 三、速率判据：滑动窗口与"窗口内无可用读数"

```
窗口长度   window_days ← 规则集该判据规则的 window_days（window_source 已在装载时强制登记来源）
窗口口径   以本轮观测日为右端点，取 observed_on 满足 (t_r − t_j) 天 ≤ window_days 且 t_j < t_r 的全部轮次
参与轮次   只取窗口内"链上最新行且非缺测"的读数：缺测轮次、被拒收轮次、被取代行一律不参与，也不补值
速率值     rate_value = max over j of |v(r) − v(j)| / (t_r − t_j)   （单位 = 字典单位/天）
触发       rate_value ≥ rate_threshold（容差 1e-9，理由见 §五）
窗口内无可用的先前读数（通常是首测轮次）  → 本轮速率判据不出结论：rate_value 为空、不触发，
                                          阈值列照常写登记值，且不计入 disabled_reasons
```

- **窗口按日历日，不按轮次序号**：`obs_round.observed_on` 才是现场事实，漏测一轮不会让窗口"缩短一轮"。
  合成数据里两者等价（等间隔），所以与 `07 §七` 的反算逐位一致，回归可对账。
- **窗口未配置 = 速率判据不启用**（`window_unconfigured`），不用默认 3 天冒充规范值；
  此时若累计判据可判，仍按 §2.3 第三行出结论。
- 取最大斜率而不是相邻两轮：跳增后回落的那一轮，最大斜率仍指向跳增的起点，这正是"速率优先于累计量"的现场形态。

## 四、预警比例判据

`ratio` 判据（`judgement=prewarning`）按**有效累计控制值的比例**提前预警：

```
生效条件   该判据阈值可用（user_input/design_value + verified + value + unit=ratio + evidence）
           且累计判据有有效阈值（比例要乘在它上面）
成立       |v(r)| ≥ ratio × cum_threshold（同一容差 1e-9）
结论       只在"两个报警判据都不成立"时把 normal 降格为 prewarning；已在报警或未闭环延续中时不参与
累计待定   该判据本轮不出结论，原因码沿用累计判据侧的原因码（不新增码，避免两套口径）
```

预警比例**本身也是阈值**：规则集里它的 `value` 留 `null`、`status` 留 `pending`，所以生产数据面上没有
prewarning 通路，全部是 `normal`/`alarm`/`undetermined`；夹具档位（§六）才把这条通路打开。

## 五、状态机：迁移、置位与清除

### 5.1 本轮状态的产生顺序（引擎唯一的执行顺序）

```
1  取本轮链上最新读数；无有效读数 → 不出行，跳到下一轮（§2.3 末行）
2  按 §二 解析两判据 → 越线集合 bases
3  bases 非空          → 本轮自发报警：state=alarm，first_alarm_round_id = 本轮，origin_basis = bases
4  bases 为空且上一状态未闭环 → 【状态保持】state = 上一状态（alarm / alarm_confirmed），
                           unclosed=1，first_alarm_round_id = 生命周期首个报警轮次，
                           trigger_basis = origin_basis（原始判据，不是本轮的）
5  bases 为空且已闭环   → 按 §四 判 prewarning，否则 normal；first_alarm_round_id 置空
6  两判据全待定         → undetermined（不参与 §5.2 的报警生命周期）
   粘性两条：已确认的行再越线仍写 alarm_confirmed（确认是人的动作，自动判定不替它撤销）；
         已报警的行不因新一轮越线被自动升成 alarm_confirmed（工具不替人签字）
7  本轮行的处置记录覆盖：confirm→alarm_confirmed，handle→alarm_handled，reobserve→不改状态
8  与上一轮状态做迁移校验（§5.2），非法即报错，不静默纠正
```

**第 4 行为什么必须"保持状态"而不是改判正常**：`ALLOWED_TRANSITIONS` 里 `alarm` 的后继没有 `normal`——
报警已经对外发出，在没有处置记录的情况下把它改回"正常"，等于工具代替监测单位消警。
所以未闭环期间状态保持，回落与否由 `cum_value`/`rate_value` 两列如实显示，`first_alarm_round_id ≠ 本轮`
即表明"这一行的报警是延续来的，不是本轮算出来的"。`SYN-YYCG` 的 `SYN-PL-04` 就是这条通路的标准例：
第 18 轮 `both` 触发，19/20/21 轮数值回落到两判据之下（16.6 → 13.0 → 9.4 → 5.7 mm，速率 0.51 mm/d < 1.0），
仍逐轮带 `unclosed=1` 且 `first_alarm_round_id` 指向第 18 轮。

### 5.2 迁移表（`contract/status.py::ALLOWED_TRANSITIONS` 落地为行为断言）

| 前态 | 允许的后态 | 关键禁令 |
|---|---|---|
| `undetermined` | `undetermined` `normal` `prewarning` `alarm` | 补上阈值后可以直接报警 |
| `normal` | `normal` `prewarning` `alarm` `undetermined` | |
| `prewarning` | `normal` `prewarning` `alarm` `undetermined` | |
| `alarm` | `alarm` `alarm_confirmed` `alarm_handled` `undetermined` | **不回 `normal`**（§5.1 第 4 行） |
| `alarm_confirmed` | `alarm_confirmed` `alarm_handled` `undetermined` | 同上 |
| `alarm_handled` | `normal` `prewarning` `alarm` `undetermined` | 闭环后可以重新报警；**不得回 `alarm_confirmed`** |

报错点两道，都只查 `contract/status.py` 那一张表（引擎不自带第二套，`test_m2_discipline.py` 断言此事）：

| 检查 | 断言 | 抓住什么 |
|---|---|---|
| 轮次间 | `prev_final → base` 必须在表内 | 状态序列本身走不通（如把未闭环的行自动改判正常） |
| 行内处置 | `base → final` 必须在表内 | 处置记录把行往表里没有的方向推（已处置回退成已确认） |

两处都抛 `ContractError`，消息带 (测点, 轮次, 项目, 前态 → 后态) 四元组；CLI 按 `errors.py` 映射为退出码 2。
处置指向一条从未报警的行时，先撞 §5.3 的「处置记录指向未报警的判定行」——同一件事的更早报错点。
`undetermined` 是"结论作废"不是"处置完成"，所以各态进 `undetermined` 都合法（阈值被撤回时必须能显式作废）。

### 5.3 未闭环的置位与清除（唯一口径）

| | 置位 | 清除 |
|---|---|---|
| 条件 | 本轮自发报警，或上一轮未闭环且本轮无自发报警（§5.1 第 4 行） | 该轮 `disposition` 出现 `kind='handle'`（且 `actor_role` 非空，DDL CHECK 把守），状态转 `alarm_handled` |
| 载体 | `alarm_state.unclosed = 1` | `alarm_state.unclosed = 0` |
| `confirm` | 不置位也不清除（已确认仍是未闭环，口径 C1） | — |
| `reobserve` | 只登记"已再观测"，不改状态也不清除闭环 | — |
| 阈值被撤回 | 不适用：状态转 `undetermined` 时该行的报警结论作废，`unclosed` 归 0 并保留 `first_alarm_round_id` 为空 | 待定值不得伪装成"已处置" |

### 5.4 全量重算，不做增量

`pmc check` 每次从第 1 轮到目标轮整段重算，再 upsert 落库（同 `(point_id, round_id, item_code)` 走 UPDATE 保 id）。
理由：修订链是追加式的，第 9 轮补一条修正读数会改变第 10 轮之后的 `unclosed` 与 `first_alarm_round_id`，
增量状态必然与链上事实分叉。全量重算同时是确定性纪律的载体——同库两次 `check` 必须逐列一致（回归里实测）。
`disposition` 靠 `alarm_state.id` 外键，所以落库用 UPDATE 而非删除重建，处置记录不会因重算而失效。

## 六、夹具档位（`tests/fixtures/`）：判定要有数值才能被验证

生产数据面一条阈值都没有（`07 §五`、口径 C7），全部判定只能是 `undetermined`。
"出货通路"必须能被证明走通，所以 M2 建夹具档位，三条边界写死：

| 边界 | 落地 |
|---|---|
| 夹具数值只当**现场录入的档位**（`kind=user_input`），不当设计文件号、不当规范条文 | `tests/fixtures/point_grades.json` 的 `registration.kind="user_input"`，`evidence` 前缀 `FIXTURE-GRADE:` 并自述"测试夹具，非设计值非规范值" |
| 夹具规则集用 `clause_ids` 指向判据条款（报警值条款），只承担**可追溯性**；其 `threshold.kind=none`、`value=null` —— 数值一律不来自该条款，条款在登记表里仍是 pending，供货通路照旧关闭 |
| 夹具 id 不得出现在 `data/` 任何文件里 | `tests/test_m2_discipline.py` 扫 `data/` 全部文件字面值，命中 `FIXTURE-GRADE`、`syn-fixture-grade`、`fx-alarm-window-*` 即红（并跑阳性对照） |
| `data/rulesets/*` 仍全 `null`/`pending` | 沿用 `test_data_discipline.test_unverified_thresholds_carry_no_numbers`；夹具规则集只放 `tests/fixtures/rulesets/` |

夹具规则集按工程分目录（`fx_lj3/`、`fx_zhdq/`、`fx_yycg/`），因为**速率窗口是工程配置事实**
（`07 §五`：日报站 3 天、隔日站 5 天、周报站 7 天），而窗口只能挂在规则上（`window_days` + `window_source`）。
`pmc check --rules-dir` 因此按工程各指一个目录；默认仍是 `data/rulesets`。
数值可与 `pmc/synth/profile.py` 同，但来源登记必须是夹具——**判定路径不 import `pmc.synth`**（口径 C5 由 AST 断言把守）。

## 七、退出码触发集合（`pmc check`）

| 码 | 触发集合 |
|---|---|
| 0 | 目标范围内每一行都可判，且无 `unclosed=1`、无 `disabled_reasons` |
| 1（降级） | ① 存在 `unclosed=1` 的行（未闭环报警）；② 存在 `state=undetermined` 的行；③ 存在 `disabled_reasons` 非空的行（判据部分不启用）——三者任一即 1 |
| 2（输入不可用） | 台账缺表 / 工程或轮次无档案 / 目标范围内没有任何观测行 / 非法状态迁移 / 契约校验（DTO 或 DDL）失败 |

`②③` 同时命中只出一个 1（降级只报一次），但报告里必须逐行给出原因码——核对队列靠它排序，
"等核对"与"代码不会判"混在一起就失去了优先级（`03 §1.2`）。

## 八、`pmc check` 输出契约

```
CHECK_SUMMARY  工程 P 轮次范围 1–N：行 X，normal A / prewarning B / alarm C / confirmed D / handled E / 待定 F
每测点一行：    工程  测点  项目  轮次  状态  触发依据  累计值/阈值  速率值/阈值(窗口)  来源  条款号  原因码
未闭环清单：    测点  项目  首个报警轮次  已延续轮数  最后读数是否回落  有无处置记录
```

- 未闭环清单单独成段并在 stdout 末尾，供人直接读"还欠几处处置"；模块 3 的 `no_intensified_after_alarm` 消费同一批行。
- 待定值行的阈值列打印 `-`，**不打印 0**（`R2` 纪律在展示层的落点）。
- `--round N` 只筛**打印**范围：落库写 1..N 全前缀，判据也从第 1 轮算起（§5.1 的 `unclosed` 是跨轮次状态，只写第 N 行会让起点外键与延续断链）。
- 退出码按**重算范围**判定，不按打印范围：否则 `--round 3` 会把第 2 轮的未闭环报警报成 0。

## 十、XLSX 输入通路（P07 拍板落在 M2 初）

只用标准库 `zipfile` + `xml.etree.ElementTree`，读 `xl/worksheets/*.xml` 与 `xl/sharedStrings.xml`，
`xl/styles.xml` 只用来认日期格式（内建 numFmt 14/15/16/17/22 视为日期/时间），日期序列号按 1900 纪元换算
（含 Excel 的 1900-02-29 兼容偏移，序列号 ≤ 59 时不修正，与 Excel 行为一致）。

**判读口径只有一套**：`xlsx.py` 产出的就是 `csvio` 的单元格矩阵，行级校验与 11 个原因码完全复用（口径 C15 不变）。
单元格取值归一化：数值单元格按 XML 里的原文本给出（不重新格式化，避免 `26` 与 `26.0` 两套口径）；
共享字符串/内联字符串按文本；布尔与错误值（`#DIV/0!` 等）当文本交给行级校验拒收；空单元格=空字符串。

文件级硬失败（沿用 `07 §八` 的清单，新增两条 XLSX 专有）：
不是合法 ZIP / 没有 `xl/worksheets/` 工作表 / 表头 8 列与契约不符 /
出现超出表头列数的单元格 / 同一文件多个观测日期 / 与已导入批次同哈希重放。
**行的列数不足**（XLSX 尾随空单元格不落盘）按空字符串补齐后交给行级校验，
因为 Excel 的稀疏存储让"少写一格"与"写了个空格"在文件层面不可区分——这一条不是放宽，是同一口径下的必然结论。
