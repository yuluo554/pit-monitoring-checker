# 08 · 规则集与条款核对（M3 定稿）

> 版本：v1（2026-10-07）
> 分工：`09` 管**双控判定**（模块 2 的阈值选取与状态机），本文件管**条款核对台账**与**频率时效检核**（模块 3）。
> 改本文件的规则 id、违规类别、原因码、`evidence_json` 字段 = 口径变更，须在 `06 §五` 记一行并重跑双解释器全量测试。
> `test_m3_discipline.py` 会逐条要求：代码里的类别 / 原因码 / 规则 id 必须先在本文出现。

## 一、本文管什么

模块 3 的输入是**已经躺在台账里的事实**：工况时间线（`working_condition.effective_from`）、
轮次日期（`obs_round.observed_on` + `is_intensified`）、观测有效性（链上最新未被取代的行）、
以及模块 2 落的 `alarm_state.unclosed`。输出是 `violation` 表的**应核实清单**。

三条硬边界（题面 §六.4、§模块 3 要点）：

1. **只报"应核实"**，不写"已确认违规 / 已认定超标"；结论列的取值集合在代码里就是一项
   （`auditor.CONCLUSION_CHOICES`），越界用词没有可以进来的位置。
2. **不重算报警**：检核层不 import `pmc.alarm`，"报警后未加密观测"直接读 `alarm_state.unclosed=1`
   （`test_m3_discipline.py` 用 AST 钉住这条）。
3. **给可核验的判定，不给文字提醒**：每条结论必须挂 `rule_id` + `clause_ids` + 可复算的 `evidence_json`，
   缺任一项就写不进库（DTO `validate()` 与 DDL `NOT NULL` 两处把守）。

- **可参与判定条数仍为 0**：`pmc selfcheck` 出「规则 17 条，可参与判定 0 条」，`pmc rulesets` 的不启用统计里

  前提不成立时，正确行为是不填数（§六.6 与禁项一），偏差说明写在 `05 §三之四`。

  ① 用户在测点档案录入设计报警值（`design_value` + 设计文件号，模块 1 已支持）；

## 三、规则集结构口径（本轮变更）

`data/rulesets/frequency_compliance.json` **version 1 → 2**。变更内容：

| 键 | 含义 | 约束 |
|---|---|---|
| `depth_max` | 本条 `interval` 规则适用的**开挖深度上限**（单位 m，含边界） | 只允许出现在 `basis=interval` 的规则上；必须 > 0；**全集合里至多一条不带 `depth_max`，即兜底档** |

为什么要分档：题面 §模块 3 要求"频率要求随开挖深度与工况变化，须支持工况变更即刻生效新频率"，
而单条规则只有一个 `threshold.value` —— 不分档就只能拿一个天数套所有工况，那正好违背这条要求。
装载校验（`rules/loader.py::Rule.validate`）拒绝把 `depth_max` 用在别的判据上，规则集键白名单同步加入
（口径 C6 的"改它的代价"已兑现：版本 +1 + `06 §五` 一行）。

`data/rulesets/alarm_dual_control.json` **不动**（仍 v1）：本轮没核对到报警值原文，任何"顺手改一版"都会让
`ruleset_applied` 的 sha256 与已生成判定对不上。`test_m3_discipline.py::test_production_frequency_rules_still_supply_no_numbers`
把这条钉住（含"报警规则集不得被顺手改版本"的断言）。

## 四、四类检核的确切定义

| 类别 | 驱动规则 | 确切定义 | 边界与为什么 |
|---|---|---|---|
| `missed` | `FREQ-MISSED-ROUND` | 排定轮次（`obs_round` 里存在的轮）× 在册测点（`install_date ≤ observed_on ≤ abandon_date`）在链上**没有有效读数**：要么一行都没入库（`gap=no_effective_observation`），要么带缺测标记（`missing_flag_marked`） | ① 已被取代的修订行不算证据（`superseded_by IS NULL`，口径 C16）；② 缺测不许被插值掩盖（模块 1 的 CHECK 保证）；③ **整轮零入库**只出一条工程级结论（`gap=round_not_imported`，`point_id` 为空），因为"这轮还没导入"与"196 个测点各自漏测"是两件事，逐测点刷屏会把清单埋掉 |
| `over_interval` | 生效的 `interval` 档规则（`rule_id` = 供出上限的那条规则 id） | 同一工况段内，相邻两轮的实际间隔 **>** 后一轮生效工况的深度档上限 | 间隔按**日历日**差（`observed_on` 的 `date.toordinal()`），与工作日均无关；首轮无前轮，不判 |
| `stale_frequency` | `FREQ-CONDITION-CHANGE`（条款按规则登记） | 工况变更后的**第一轮**，间隔超过**新**工况的档上限 | "变更当轮即按新频率判"的落点。同一次间隔只归一个类别：变更段归 `stale_frequency`，段内归 `over_interval`，不重复计数。若 `FREQ-CONDITION-CHANGE` 不生效，则仍报 `over_interval` 并记 `condition_change_blocked`（事实照报，归因不硬编） |
| `no_intensified_after_alarm` | `FREQ-INTENSIFY-AFTER-ALARM`（条款含 `MOHURD-37`） | 对每个仍**未闭环**的报警（按 `测点 × 监测项目` 聚合，起点取 `first_alarm_round_id`，缺失时退回最早的未闭环轮次），检核范围内**没有任何** `is_intensified=1` 的轮次 ≥ 该起点 | 只读 `alarm_state.unclosed`，不重算报警（§一.2）。已处置（`unclosed=0`）的不进清单。若该工程 `alarm_state` 一条都没有 → 记 `alarm_state_empty` 并说明"先 pmc check"，**不得**当成"没有违规" |

### 四之一、档位的选取次序（`_interval_band`）

1. 取当前生效工况的 `excavation_depth`；
2. 在**生效的** `interval` 规则里按 `depth_max` 升序找第一条 `depth ≤ depth_max` 的档（边界含等号，容 1e-9 浮点余量）；
3. 找不到就用兜底档（`depth_max` 为空）；档案未登记深度时**只能**用兜底档并记 `excavation_depth_unrecorded`；
4. 三者都没有 → 记 `no_applicable_interval_band` 并**不判**。第 4 步是本工具与"顺手给个默认 3 天"的分界线（D07 同一理由）。

工况本身按 `working_condition.effective_from` **日期**定档（`03 §2` 就把这一列标为模块 3 的支撑点），
轮次上的 `condition_id` 只作台账自述；轮次日期早于全部 `effective_from` → `condition_not_recorded`，不硬编一个工况。

## 五、原因码：检核轴（与阈值轴、引擎轴分账）

阈值轴 9 码在 `contract/thresholds.py`（口径 C2），引擎轴 2 码在 `alarm/engine.py`（C2b / D33），
**检核轴 5 码在 `compliance/auditor.py`**（本表是唯一定文处）：

| 原因码 | 触发场合 | 面向用户的含义 |
|---|---|---|
| `no_applicable_interval_band` | 生效工况的深度取不到任何上限档 | 缺"每档几天"的数值：处置动作是补规则集档位，不是改代码 |
| `excavation_depth_unrecorded` | `working_condition.excavation_depth` 为空 | 档案缺事实：处置动作是补工况深度 |
| `condition_not_recorded` | 轮次日期早于台账内所有工况的 `effective_from` | 工况时间线起点晚于观测：按哪个频率判无从确定 |
| `alarm_state_empty` | 该工程 `alarm_state` 零行 | 还没跑 `pmc check`：报警后加密观测无从对账，**不等于合规** |
| `condition_change_blocked` | 工况发生了变更，但 `FREQ-CONDITION-CHANGE` 不生效 | 超限事实仍报 `over_interval`，只是不冒充"未按新频率"的归因 |

规则级不生效原因（`FREQ-*` 挂在哪个门控码上）沿用 `rules/gate.py` 的既有集合，`pmc audit` 的 `AUDIT_QUEUE` 逐条打印，
**"没有已核对依据"与"检核本身判不动"必须分开统计**（`03 §1.2` 的同一理由）。

## 六、`evidence_json` 字段表（M5 报告与追溯清单读这张表）

| 类别 | 必有字段 | 说明 |
|---|---|---|
| `missed` | `item_code` / `round_index` / `observed_on` / `condition_code` / `gap` / `detail` | 工程级那条另有 `points_expected`，`item_code` 省略 |
| `over_interval` / `stale_frequency` | `gap_days` / `limit_days` / `band_rule_id` / `band_depth_max` / `prev_round_index` / `prev_observed_on` / `observed_on` / `condition_code` / `prev_condition_code` / `excavation_depth` / `detail` | `band_depth_max` 为空即兜底档；`prev_*` 两个字段是"间隔"这一判据的可复算证据 |
| `no_intensified_after_alarm` | `item_code` / `first_alarm_round_index` / `unclosed_rounds` / `latest_unclosed_round_index` / `audited_to_round_index` / `intensified_rounds_in_scope` / `detail` | `unclosed_rounds` 直接来自模块 2 的落库行 |

`detail` 是人读的一句事实陈述（含数字与工况 code），不带任何"违规/超标"定性词。

## 七、`pmc audit` 输出契约与退出码

```
pmc audit --db PATH [--project CODE] [--from N] [--to N] [--rules-dir DIR]
```

`--data-dir` 是全局参数，必须写在子命令**之前**（`pmc --data-dir DIR audit --db …`）；
`--rules-dir` 与 `check` 同义：按工程配置的频率档从这里进来，缺省 `data/rulesets`。

| 行 | 内容 |
|---|---|
| `AUDIT_SCOPE` | 工程、轮次档案跨度、检核范围轮数、台账内加密观测轮次、落库新增/清除计数 |
| `AUDIT_SUMMARY` | 四类各自条数 + 总数（口径固定按 `missed over_interval stale_frequency no_intensified_after_alarm` 顺序） |
| `AUDIT_CLAUSE <条款号>` | 该条款下的应核实条数（题面 §模块 3"逐条挂条款号"的分组视图） |
| 明细行 | `工程 类别 测点 轮次 规则 条款号 结论 证据`，结论列只取 `应核实`；测点或轮次不适用时打 `-` |
| `AUDIT_QUEUE` | 不生效的频率规则条数 + 检核缺口条数，随后逐条给 `rule_id reason=<码>` 或 `<原因码>：<说明>` |

**退出码触发集合**（`auditor.degraded_exit`，与 `09 §七` 并列为第二张表）：

| 码 | 条件 |
|---|---|
| 0 | 无应核实事项 **且** 无被门控挡住 **且** 无检核缺口 |
| 1 | 三者任一（题面 §二 纪律：存在未核对依据即降级） |
| 2 | 台账缺文件/缺表、工程不在台账里、工程没有任何轮次档案、`--rules-dir` 不存在、契约校验失败 |

多工程（不带 `--project`）时逐个工程打印自己的三段头，退出码取各工程的最大值。

**落库方式是整段替换**：`DELETE FROM violation WHERE project_id=?` 后重插。理由与 C20 同源——
`violation` 表没有唯一键，增量写会让上一轮的结论残留成"历史违规"，而检核的输入事实
（链上最新行、`unclosed` 标记）本来就是追加式的，只有整段重算才对得上。重跑两次得到同一集合，
`test_cli_m3.py::test_rerun_replaces_the_list_instead_of_accumulating` 逐字断言 `落库 新增 26 / 清除 26`。

## 八、夹具数据面：怎么在"一条依据都没核对"的前提下证明通路

`test_alarm_engine.py` 的做法是**内存构造**规则与条款；模块 3 的端到端还需要整条台账链，
因此新增 `tests/fixtures/data_freq/`（`clauses/register.json` + `rulesets/frequency_compliance.json` + 空 `dict/` 占位）：

- 它是 `find_data_dir` 认得的**完整数据目录替身**，`--data-dir` 指过去就能让频率条款"看起来 verified"；
- 上限天数 **7 / 3 / 2 天**（深度 ≤5m / ≤10m / 更深）是**合成工程档案的配置事实**
  （`synth/sites.py` 的三站间隔 1/2/7 天与工况深度 3.5–14.5 m 就摆在那里），不是规范值；
- 每条夹具记录都带 `FIXTURE-FREQ` 与 `fixture_id=syn-m3-fixture-1` 自述「非已核对条文」；
  `FIXTURE_MARKERS` 扩容后，这些串只要出现在 `data/` 就当场红（`test_m2_discipline.py` 的扫描 + 阳性对照）；
- 口径 C21 因此延长一句：**频率档位的夹具数据面也只能待在 `tests/fixtures/` 下**，
  转 `verified` 的唯一合法入口仍是 §二 那条渠道登记。

两站对照（`test_cli_m3.py` 实测逐条断言）：

| 工程 | 台账内加密轮次 | 未闭环报警起点 | 结论 |
|---|---|---|---|
| `SYN-ZHDQ` | R10 / R11 / R12 | R9、R11（被覆盖）；R14、R17（之后无加密轮次） | 前者不报，后者两条点名 |
| `SYN-YYCG` | 无 | R18、R22 | 两条全数点名 |

`SYN-YYCG` 的四段工况（R1/R9/R17/R25，深度 5→10→14.5→14.5 m）给出：
C1 周报合规（零结论即结论）、R9/R17/R25 三条 `stale_frequency`、段内 19 条 `over_interval`。
`SYN-ZHDQ`（隔日 2 天、深度 4→8→8 m）间隔类零结论，漏测两条（R12 单位错误被拒收 → 无入库行；R16 缺测标记）——
**这正是"检核不是报告生成器"要证的**：合规处不吭声，缺口处点名并给出可复算的天数。

## 十、M4 接手时要知道的三件事

1. **频率检核没有基准指标**：`bench`（M4）的口径是模块 2 的召回/误报/首超定位误差；
   检核侧只做逐条对账（本文件的实测条数就是期望值），要出"漏检率/误检率"必须先有第二套真值 —— 属范围外。
2. **`violation` 表是 M5 报告的第二数据源**：追溯清单要能把一条应核实事项指回 `rule_id` + 条款 + 台账轮次行，
   所以 `rule_id` 与 `clause_ids` 的稳定性按契约对待（改 id 先改本文 §四）。
3. **生产数据面的 verified 计数仍是 0**：M6 交付前，任何"可参与判定 N 条（N>0）"的截图都只能来自夹具数据面，
   README 的指标表不得因此写"达标"（C11）。
