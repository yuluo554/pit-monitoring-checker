# 11 · 成果报告与桌面交付口径（M5）

> 本文件是 M5 的单一事实源：报告形态、工作表名、追溯口径、签字栏纪律、打包红线。
> `tests/test_m5_discipline.py` 会逐个把这些常量与文档对账，改了代码不写文档就是红。

## 一、报告三形态（`pmc report --kind …`）

| 形态词 | 名称 | 缺省范围 | 目标轮次参数 |
|---|---|---|---|
| `daily` | 监测日报 | 单轮次；不给 `--round` 时取台账里最晚的一轮 | `--round N` 只与 `daily` 搭配 |
| `weekly` | 监测周报 | 台账最晚观测日期往前 7 天（含端点）命中的轮次 | 用 `--from/--to` 覆盖 |
| `stage` | 监测阶段报告 | 台账全部轮次 | 用 `--from/--to` 截取 |

`--round` 与 `weekly`/`stage` 同时给出 → `InputError`（退出码 2），不做"猜一个范围"的兜底；
`--from > --to` 同样直接拒。文件名固定 `pmc-<kind>-<工程编码>-<轮次范围>.xlsx`，
**文件名与内容都不带时间戳**（时间戳会让"两次导出逐字节一致"无从断言）。

## 二、工作表构成（顺序即表序，`SHEET_ORDER`）

| 表名 | 内容 | 数据来源 |
|---|---|---|
| `报告说明` | 工程身份、覆盖轮次逐轮清单、台账内容指纹、规则集版本、边界声明、留空的生成时间 | `project` / `obs_round` / `ruleset_applied` |
| `异常测点清单` | 报警 / 预警 / 已处置 的判定行 + 处置记录列 | `alarm_state` + `disposition` |
| `报警台账` | 本期全部判定行（含 `normal` 与 `undetermined`） | `alarm_state` |
| `未闭环清单` | `unclosed` 标记为真的判定行；本轮已回落但未处置的单列标注 | `alarm_state` |
| `合规检核` | `pmc audit` 落的应核实事项，结论用词固定「应核实」 | `violation` |
| `基准对账` | 仅 `--bench-plane` 给出时存在；逐起结论取 `BenchReport` 的 `outcome` 原文 | `pmc bench --json` |
| `过程线数据` | 测点 × 轮次 × 累计值 + 累计控制值，同一张表上挂原生 chart | `observation`（链头）+ `point` |
| `签字栏` | 四个角色 + 空白签字/日期列 + 台账指纹核对 | 固定文案 |
| `追溯清单` | 报告内每个含数字单元格的 `(表, 行号, 列)` | 构造期登记 |

判定与检核的**读法只有一条**：读落库行，不读内存 DTO，且只认 `superseded_by IS NULL` 的链头
（与 C16 / C20c 同一条纪律）。报告层不 import `pmc.alarm` / `pmc.compliance` / `pmc.rules`，
所以它结构上无法重算判定（`test_m5_discipline.test_report_does_not_compute_anything_the_engine_owns`）。

## 二之二、状态与触发依据用词（渲染层，不新增词汇）

状态码就是 `contract/status.py` 的六个值，报告只做"码 → 中文"的渲染映射，
`assert_vocabulary()` 断言两侧集合逐字相等（C1 / C22：多一个少一个都是红）。

| 状态码 | 报告用词 | 是否进异常清单 |
|---|---|---|
| `normal` | 正常 | 否 |
| `prewarning` | 预警 | 是 |
| `alarm` | 报警 | 是 |
| `alarm_confirmed` | 报警已确认 | 是 |
| `alarm_handled` | 报警已处置 | 是 |
| `undetermined` | 待定值 | 否（进报警台账与核对口径） |

触发依据同表：`cumulative` 累计量判据、`rate` 速率判据、`both` 双控同时触发、`none` 无。
处置记录用词与 DDL 的 `disposition.kind` 对齐：`confirm` 已确认、`handle` 已处置、`reobserve` 已复测。
检核类别与 `violation.kind` 对齐：`missed`、`over_interval`、`stale_frequency`、`no_intensified_after_alarm`；
结论列固定「应核实」（C2c，报告不写"已确认违规"）。

## 三、追溯口径（DoD「无来源不明数字」）

- 规则：单元格值若是数值，**或**文本里含 ASCII 数字，就必须带来源 `(表名, 行号, 列名)`；
  缺来源在构造期抛 `ReportError`，不是事后检查（阳性对照见
  `test_positive_control_numeric_cell_without_source_is_rejected`）。
- 逐格对账：`test_every_digit_bearing_cell_is_traced` 解析每张工作表 XML，
  把含数字的单元格与 `追溯清单` 第一列逐个比对，`追溯清单` 本身除外。
- 汇总类单元格（如「覆盖轮次数」）逐个来源展开：一个贡献行一条 `TraceRow`，
  与 `contract/records.py::TraceRow` 同一套 DTO，报告层不另立追溯对象（C22）。
- 派生来源（不是"一行台账"）登记在 `DERIVED_TABLES`，只有两个：
  - `bench`：`row_id` = 该 JSON 里 `events` 的下标，查法列写复现命令；
  - `ledger_fingerprint`：台账内容 sha256，算法在 `pmc/report/fingerprint.py`。
- 台账表里无整型主键的表（`ruleset_applied`）按主键排序取行序（1 起），查法列写 `ORDER BY … LIMIT 1 OFFSET n-1`。
- 固定文案表 `STATIC_TEXTS` 里的句子**不得含数字**（`assert_vocabulary` 把守）；
  要写数字就得改成带来源的数据行。规范编号（如条款号）属标识符，逐个挂 `alarm_state.clause_ids` 来源。

### 指纹为什么剔除时间列
`import_batch.imported_at` / `disposition.acted_at` / `ruleset_applied.applied_at` 记录"何时"，
不记录"是什么"。同一批数据重复导入必须得到同一个指纹，否则签字栏每次核都对不上，指纹就退化成装饰。

## 四、xlsx 写出侧纪律

标准库 `zipfile` + 手写 OOXML（`06 D03` / `D34`）：不装 openpyxl / xlsxwriter / pandas。

- `ZipInfo` 日期固定 `1980-01-01`，`docProps/core.xml` 的 creator/lastModifiedBy 写 `pmc` 占位，
  created/modified 写 `1980-01-01T00:00:00Z`；
- ZIP 条目按名字排序写入，压缩级别显式写死 `6`（不显式则随解释器默认，属隐式输入）；
- 文本走 `inlineStr`，不建 `sharedStrings.xml`（少一处顺序不确定源）；
- 关系部件（`*.rels`）**只靠 `<Default Extension="rels">` 定内容类型**，
  给它们写 `<Override>` 会让 OPC 判定"PackageRelationship 部件内容类型不对"、整包打不开
  —— 这条已由 `content_types_xml` 直接拒绝 + `test_content_types_rejects_rel_override` 反证；
- 图表是 xlsx 原生 chart（`xl/charts/chartN.xml` + `xl/drawings/drawingN.xml` + 工作表 `<drawing>`），
  不是贴图：类别轴用轮次标签、值轴用累计值列、阈值另作一条**虚线系列**（`prstDash val="dash"`），
  每个测点一张图，最多绘制 `6` 张（`CHART_SERIES_CAP`），超出只不进图、数据行仍在表里；
  没有异常测点时按测点编码顺序取前若干条，保证图表恒在。

产物已在开发机用第三方 OpenXML 解析器复验：工作簿可打开、`过程线数据` 识别出 4 张图、
文档检查器 0 issue（见 §七 实测记录）。

## 五、签字栏与免责（题面 01 §六.1、§模块 4）

- 角色固定四个：`编制人（监测）`、`审核人（监测单位）`、`总监代表`、`业主代表`；
- 签字与日期两列**程序永不填写**，导出即空白；空白栏旁边一行写死
  「本栏空白即未审核，程序不填写」；
- 报告不含"已审核""已处置"这类断言：处置状态只来自 `disposition` 表，
  无记录就写「台账内无处置记录」；
- 每份报告在 `报告说明` 与 `签字栏` 两处带边界句：
  **本报告不判定基坑是否安全**，不替代监测、设计、施工、监理的判断与处置决策；
- `报告生成时间` 一格留空由使用方填写，不进文件元数据。

## 六、退出码（并入 C4）

`pmc report` 的降级判定：`未闭环`、`待定值`、`应核实事项` 任一非零，或随附基准报告自身未达标 →
退出码 `1`（`EXIT_DEGRADED`）；报告成功产出且无上述项 → `0`；
工程不存在 / 无轮次档案 / 无判定行 / 参数组合非法 → `2`（`EXIT_INPUT_UNAVAILABLE`）。
报告层没有实现中的分支，所以不再返回 `3`。

### 机器可读标记行（供门禁与文档逐行对账）

`pmc report` 在 stdout 上打这七类标记行，词面即契约（`REPORT` 前缀）：

| 标记 | 内容 |
|---|---|
| `REPORT_FILE` / `REPORT_DRYRUN` | 产物路径 + 内容 sha256 前 12 位（dry-run 不落盘） |
| `REPORT_SHEETS` | 工作表顺序，竖线分隔 |
| `REPORT_SCOPE` | 工程、形态、轮次范围、判定行数、异常数、未闭环数、待定值数、检核数、追溯行数、过程线图数 |
| `REPORT_TRACES` | 指向追溯清单表名 |
| `REPORT_BENCH` | 随附基准的逐起条数与它自己的退出码 |
| `REPORT_BOUNDARY` | 边界声明原文 |

界面侧的存活标记是 `GUI_SMOKE_OK`（`pmc gui --smoke`），台账通路沿用 M1–M4 的
`SELF_CHECK_OK` / `SYNTH_CHECK_OK` / `IMPORT_RECEIPT` / `CHECK_SUMMARY` / `AUDIT_SUMMARY` / `BENCH_*`。

## 八、PySide6 界面（五页签）

- 页签顺序固定：`台账`、`导入`、`判定`、`检核`、`报告`；顶部共用"台账路径 / 工程编码 / 数据目录"；
- **界面不另起第二套行为**：每个页签把输入拼成 argv 交给 `pmc.cli.main()` 在进程内执行，
  抓回终端那份文本原样显示（`test_ledger_page_text_matches_cli_exactly` 逐字对账）；
- 参数面是 CLI 的子集：`test_argv_flags_exist_on_the_cli` 拿 argparse 的 dest 集合逐个校验，
  界面凭空造旗标就是红；
- PySide6 只进 `gui` extras，`app.py` 顶层不 import Qt；缺依赖时 `pmc gui` 打印安装提示并返回 2，
  `pip install -e ".[dev,gui,pkg]"` 后 `pmc gui --db …` 起界面；
- 反馈走 `page.notify()` 写页内日志区，**不用模态框**（offscreen 测试批会被模态框挂死）；
  文件对话框只存在于按钮槽，测试不点那条分支；
- `--smoke`：只构造窗口不进事件循环，打印 `GUI_SMOKE_OK 页签 5 个：…` 并返回 0，
  同时作为打包后"界面能起来"的存活探针。

## 九、PyInstaller 桌面交付（onedir 双 exe）

- 两个入口共用同一份内核：
  - `pmc.exe`（`console=True`）：与 `pmc` 脚本同一 main，是没有 Python 的机器上的**脚本化验证通路**
    （`selfcheck` / `rulesets` / `synth --check` / `bench` / `report` 全可跑）；
  - `pmc-gui.exe`（`console=False`）：桌面界面；
- `datas` 白名单只收运行必需数据：整份 `data/`（字典、规则集、条款登记、合成时序、真值、golden），
  不收 `tests/`、`plan/`、`.tmp_*`；
- 冻结通路：`find_data_dir` 的优先级为 **显式参数 > `PMC_DATA_DIR` > `sys._MEIPASS/data` >
  `exe目录/_internal/data` > 仓库根 > 当前目录上溯**（`src/pmc/paths.py`）。
  优先级变更属口径变更：会让"内嵌数据"验证退化成"命中仓库 data"的假绿；
- exe 验证必须在**中立目录**跑（临时目录 + 剥离 `PYTHONPATH`），
  在仓库树内跑会沿 CWD 上溯命中仓库 `data/`，内嵌通路验了个寂寞；
- 构建通道与版本、红线审计结论见 §十 与 `plan/05` 的 M5 偏差表（构建实跑后回填，不预填）。

## 十、构建红线（`scripts/dist_audit.py`）

硬门（任一违反 → 退出码 1，`DIST_AUDIT_OK` 不打印）：

1. `dist/` 顶层只允许白名单目录（两个 onedir），不许多出别的产物；
2. 内嵌 `data/` 与仓库 `data/` **整目录相对路径逐份 sha256 对账**，不许少一份也不许多一份
   （只比顶层文件不算对账：子目录里的语料会根本没参与比对）；
3. 产物树内不得出现禁区成分：`plan/`、`tests/fixtures`、`.tmp_verify`、`.tmp_parse`、抓取缓存；
4. 我们自己的载荷（`data/` 内嵌件、报告产物）内不得含：`http(s)` 外链、盘符绝对路径、
   本机用户名与 home 路径、真实创建时间；扫描用**运行时取到的用户名/home**当诱饵样本；
5. 报告字节复现：exe 内连续两次导出同一份日报必须逐字节一致。

复核项（如实留档、不静默放行）：PyInstaller 会把构建目录写进 `.pyc` 的 `co_filename`，
故"产物字节里 0 盘符路径"对第三方冻结载荷不成立。开发机的仓库根路径本身不含用户名，
构建即用该路径；用户名/home 两类**个人标记**仍按硬门扫，0 命中才算过。

审计器自身要有反证：用伪造 dist（少一份内嵌语料 / 多一个 `plan/` 目录 / 改一个子目录字节）
逐项验证各类违反都会被点名，否则 `DIST_AUDIT_OK` 的含金量无从谈起。

`--selftest` 现有 9 项反证，全部随全量测试常驻（`tests/test_m5_packaging.py`）：
合格产物不误报、少一份语料、多一个 `plan/` 目录、改一个字节、多出文件、
合格报告不误报、报告含 home 路径、报告 `.rels` 含外部 Target、报告正文含 URL。

### 误报校准四项（本轮实踩并修好）

1. **盘符正则要吃掉 URL scheme**：`[A-Za-z]:[\\/]` 会把 `https://` 里的 `s:/` 当盘符，
   于是 `clauses/register.json`（合法登记渠道 URL）被判"内嵌件含盘符路径"。
   改为带字母环视 `(?<![A-Za-z0-9])[A-Za-z]:[\\/]`；
2. **`.rels` 的命名空间 URI 不是外链**：`xmlns="http://…"` 是 OOXML 规范写法，
   对 `.rels` 全文做 http 子串扫描会把每份真报告判红。改为只看 `TargetMode="External"`
   与 `Target="http…|file…"`；
3. **工作表正文要剥标签再扫**：`<worksheet xmlns="http://…">` 的标签里全是 http，
   剥掉标签后看正文才是"用户可见外链"；
4. **spec 白名单按 AST 取**：spec 的注释本来就要写"什么不许入包"，
   按全文子串判会把 `plan/` 这类词当违规（`test_spec_datas_is_a_whitelist_without_tests_or_plan` 首版即误报）。

| 判定 | `pmc.exe check --db … --project SYN-ZHDQ --round 1` | `undetermined=196`，退出码 1 —— **生产数据面没有已核对阈值，这是设计行为** |
| 报告 | `pmc.exe report --kind daily … --out …` 连续两次 | 退出码 1（含待定值即降级），两份文件 `BYTE_IDENTICAL` |
| 基准反证 | `pmc.exe bench --plane ledger` | 退出码 1，指标面「不可用」，与源码态一致 |
| 界面存活 | `pmc-gui.exe --smoke --db …` | 退出码 0，`GUI_SMOKE_OK 页签 5 个` |
| 越界输入 | `pmc.exe report --kind bogus …` | 退出码 2，argparse 拒绝，不静默接受 |

两条如实留档的观察：

1. exe 内跑出的"待定值 → 报告"通路是**诚实降级**，不是缺陷：报告能出、每个数字可回溯、
   但阈值列全空并带原因码。数值通路仍只有两条合法入口（用户录入档案值 / 材料到位后按 `08 §三` 填），
   本轮**没有**为了让报告里出现数字而把夹具档位搬进 `data/`（禁项一）；
2. 中文输出在把 exe 的 stdout 重定向到文件时按控制台代码页（cp936）写入，用 UTF-8 解码会显示乱码，
   与源码态 `python -m pmc` 不带 `-X utf8` 的表现一致 —— 不是冻结层的缺陷，
   验证脚本按代码页读或直接看真实控制台即可。
3. 测点档案数值的**录入入口**（GUI 表格编辑或 `pmc point-set` 类命令）本轮未做，
   所以 exe 现场演示的报警形态报告只能用已判定落库的台账；这是 M6 之后的一条待补通路（见 `HANDOFF-M6`）。
